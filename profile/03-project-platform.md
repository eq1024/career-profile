# 项目深挖：跨境售后与仓储管理系统（Vue 3 Monorepo 重构）

> 角色：新版全权独立负责——架构设计、技术选型、核心实现、部署。旧版负责维护与功能迭代。
> 时间：2024.08 — 至今（2026 年进入重构与规模化阶段）
> 关键词：Monorepo、共享包边界、配置驱动、RBAC、SSE、i18n、可观测性、扫码规则、流程节点表单

---

## 1. 一句话定位

把 3 个各自维护、大量复制粘贴的 Vue 2 仓库，重构为 1 个 Monorepo + 3 个应用 + 10 个共享包，并用配置驱动把 69 个列表页变成"零前端页面代码"。重点不是换框架，而是**重新划边界**：哪些代码该共享、哪些该留在应用、依赖只能往哪个方向走。

---

## 2. 背景与约束

- 旧版由 3 个独立仓库组成：管理后台、服务端后台、客户端后台。
- HTTP 封装、工具函数、权限逻辑在三处几乎完全相同，但各自维护。
- 一个 Bug 要改三次，一个功能要做三遍；接口注册表约 1,600 条，存在大量重复。
- UI 库混用（多套组件库并存），交互与视觉不一致。
- 维护期间发现并记录了 17 项安全与技术债，包括监控 token 硬编码、依赖 CVE、路由权限形同虚设、Store 膨胀、Source Map 暴露、Mock 死代码等。
- 业务仍在高速迭代，重构不能停业务；需要**渐进式替换**，而不是推倒重来。

---

## 3. 架构总览

```text
apps/
  admin/      管理后台：权限、客户、仓储、产品、物流、报价、自定义表单
  server/     服务端后台：售后、入库、库存、出库、翻新、售后工作台、打印
  client/     客户端后台：产品、订单、售后、开发者中心

packages/
  config          环境变量统一读取
  utils           SSE / 事件总线 / 日期 / 扫码规则
  fetch           HTTP 客户端工厂 + API 模块
  i18n            Vue I18n 封装 + 三语词条
  ui              共享组件 + 列表引擎 + 表单引擎
  permission      hasPermission() + v-permission
  stores          Pinia Store 工厂
  icons           菜单图标注册表
  label           标签打印定义
  observability   OpenObserve RUM + 浏览器日志（2026.08 新增）
```

**依赖方向严格单向**：`config → utils → fetch / i18n → ui → apps`。共享包不反向依赖应用；应用之间互不依赖。

## 4. 关键决策

### 决策 1：用 Monorepo 统一三端，而不是继续三仓库

**问题**：三仓库复制粘贴导致"一个 Bug 三份工"，且共享逻辑无法版本化。
**方案**：pnpm workspace + Turborepo；三个应用保留独立构建与部署，共享代码抽包。
**取舍**：Monorepo 会增加依赖管理复杂度，但收益远大于成本；三端部署仍然独立，不强行合并成一个应用。
**结果**：共享包 0 → 10；源码规模减少约 85%。

### 决策 2：共享包只共享"稳定契约"，不共享业务页面

**问题**：把所有东西都塞进共享包，会导致包越来越臃肿、改动牵连三端。
**方案**：
- 100% 相同的逻辑 → 抽共享包
- 90% 相同但有差异 → 工厂函数 + 配置化
- 差异太大 → 留在各自应用
**例子**：认证 Store 用 `createAuthStore({ portal, api, router, extraState })` 工厂；三端共享逻辑，但各自注入 portal、仓库上下文等差异。
**结果**：共享包保持可维护，应用保留业务灵活性。

### 决策 3：HTTP 客户端用工厂 + 依赖注入

**问题**：三端都需要 Token、401 跳转、错误提示、浏览器指纹，但各自的登录态与路由不同。
**方案**：
- 共享 HTTP 客户端工厂：拦截器逻辑统一
- 应用注入 handlers：getToken / clearToken / showError / redirectToLogin / getCustomHeaders
- 服务端应用额外注入仓库上下文请求头
- 响应拦截器直接解包 data；GET 自动追加时间戳防缓存
**结果**：请求层逻辑三端一致，应用只关心"注入自己的实现"。

### 决策 4：配置驱动 CRUD 引擎——让列表页不用写

**问题**：旧版 60+ 业务模块，每个都要手写筛选、表格、分页、弹窗表单、校验。
**方案**：
```text
路由 meta.pageCode
  → GET /page-configurations/{pageCode}
  → 后端下发 columns / filters / buttons
  → DynamicListPage 渲染
  → GET /resources/{pageCode} 取数据
  → 列配置持久化到 localStorage（按 pageCode）
```
- 详情/编辑页仍保留本地 Vue 组件懒加载（复杂交互不强行配置化）
- 配套 FormDesigner：拖拽生成 Schema → 导出 JSON → 粘贴到后端 → 上线
- CustomActionForm：16+ 字段类型、条件显隐、远程选项、级联清空
**结果**：69 个唯一 pageCode 的列表页零前端页面代码；三端共 114 处 pageCode 引用。

### 决策 5：RBAC 四层权限

**层次**：
1. 认证：Token + 登录态
2. 路由级：动态路由 / 菜单权限
3. 按钮级：`v-permission` 指令（无权限直接移除 DOM）
4. 接口入口：请求层统一鉴权（最终校验在后端）
**细节**：权限码分层（模块 / 页面 / 操作），支持"任一码"判断；权限编辑器可视化配置。
**取舍**：前端权限只负责体验与入口控制，不把安全边界放在前端。

### 决策 6：SSE 全局单例 + 多事件订阅

**问题**：多个页面都需要实时通知/任务状态，如果每个页面各建一条 SSE 连接，会造成连接风暴与服务端压力。
**方案**：全局单例连接 + 事件总线；按事件类型订阅；断线自动重连；页面卸载只取消订阅，不关闭全局连接。
**结果**：三端共享一套实时消息基础设施。

### 决策 7：三语 i18n 与"文案门禁"

**规模**：中 / 英 / 德三语，3,000+ 词条。
**方案**：
- 共享 i18n 包统一初始化
- 业务词条按模块拆分
- 语言包 key 一致性校验
- 硬编码中文扫描（规则 + 评审）
- 逐步把"新增文案必须走 i18n"变成提交约束
**取舍**：国际化不是"加一个 JSON"，而是长期治理；先把基础设施做好，再逐步清理历史硬编码。

### 决策 8：抽出独立可观测性共享包

**问题**：三个应用都要 RUM 与日志，各接各的会出现配置漂移、重复代码、漏接。
**方案**：
- 独立共享包：OpenObserve RUM + 浏览器日志
- 环境变量驱动：enabled / site / token / org / appId / service / env / 隐私等级 / 回放采样率
- token 未配置或仍是占位符时不初始化（本地开发零配置、不发无效请求）
- 登录绑定用户、登出清除用户
**结果**：三端行为一致，应用只注入自己的 appCode。

### 决策 9：配置驱动从列表页延伸到流程节点

**场景**：开箱检测是"开箱前 → 产品检测 → 封箱"的节点式流程，每个节点的表单由服务流程模板配置下发。
**方案**：
- 节点完成状态以后端为准；前端计算"前置节点完成后才解锁"、"整单完成后只读"
- NodeFormPanel 把服务流程模板 config 渲染成表单，只负责取表单、校验、收集 output_data；提交时机交给父组件
- 同一面板复用在：订单级节点内嵌 + 产品检测节点行内弹层（按子单号）
- 产品列表的增删改查继续走 pageCode 配置驱动
**意义**：从"列表页零代码"升级到"流程节点零代码"。

### 决策 10：v-scan 扫码指令 + 跨端扫码规则

**场景**：仓库工作台大量使用键盘型扫码枪，物流单号常带渠道前后缀，需要按规则裁剪。
**方案**：
- 规则引擎：conditions（长度 / 包含 / 前缀 / 正则）+ value_rules（取子串 / 分割 / 后处理替换）
- v-scan 指令：绑定在输入框上，回车时套规则；命中即写回并同步 v-model，未命中不拦截
- 与移动端共用同一套规则结构
**取舍**：Web 端不做"极速连击/扫码枪"判别，只在回车瞬间判一次——无逐键开销、代码简单；代价是手动输入命中规则也会被改写，因此规则只挂在扫码字段上。

### 决策 11：Tauri v2 双窗口方案（设计完成，未落地）

**方案**：双窗口 + 多进程隔离 + CSP 白名单（只允许后端域名）。
**状态**：完成方案设计与风险评估，未进入完整实现。资料中明确标注，不夸大为实战。

## 5. 工程化难点：Monorepo 的真实坑

### 5.1 pnpm 严格模式：import 的包必须自己声明

npm/yarn 会把依赖拍平，pnpm 不会。共享包 import 了某个库，就必须在自己的 package.json 里声明，否则即使别的包装了也会报错。这条约束逼着依赖边界保持清晰。

### 5.2 Singleton 库必须用 peerDependencies

Vue、Pinia、Vue Router、Element Plus、Vue I18n 等全局只应有一个实例。如果共享包把它们写进 dependencies，版本范围不匹配时可能装两份——两份 Pinia = 两个 store 注册表，store 互相找不到。解决：singleton 库放 peerDependencies；根上用 pnpm overrides 兜底。

### 5.3 路径别名在共享包里不解析

`@/` 是各应用自己定义的别名，共享包不能依赖它。解决：共享包通过参数接收宿主实例（依赖注入），不反向 import 应用代码。

### 5.4 Store 用工厂函数，而不是强行全量共享

三端 auth / permission / settings / tabs 结构相似但配置不同。强行抽成一个包会塞满 portal 判断。解决：`createAuthStore(options)` 工厂，共享逻辑、配置差异。

### 5.5 共享包的 Vue 组件需要 vue 才能类型检查

即使运行时不打包 vue，组件库也需要在 devDependencies / peerDependencies 中声明 vue，否则 IDE 类型提示与构建检查会出问题。

## 8. 取舍与不足

- **测试覆盖有限**：优先补了类型检查、Lint、i18n 门禁；单元测试 / E2E 仍在补强。
- **TypeScript 迁移是渐进的**：新版先保证结构与边界，TS 作为后续迁移目标，不强行一次性重写。
- **Tauri 未落地**：只完成方案设计，不把它写成"已交付"。
- **配置驱动不是万能**：复杂详情/编辑页仍保留本地组件，避免为了"零代码"牺牲可维护性。

## 9. 面试追问与回答要点

1. **为什么用 Monorepo，而不是 npm link / git submodule？**
   - 三端需要同一版本、同一构建链、同一依赖图；submodule 仍然要多次发布，link 不适合 CI；workspace 能保证原子提交和统一版本。
2. **共享包边界怎么划？**
   - 100% 相同抽包；90% 相同用工厂 + 配置；差异大就留在应用。共享包只向上依赖。
3. **两份 Pinia 会怎样？**
   - 两个独立 store 注册表，组件拿不到另一个实例注册的 store；用 peerDependencies + overrides 防止。
4. **配置驱动引擎的边界在哪？**
   - 列表/筛选/分页/标准表单配置化；复杂交互仍用本地组件。详情页保留懒加载组件。
5. **69 个列表页零代码，怎么保证不失控？**
   - pageCode 是契约；后端下发配置；列设置持久化；表单设计器产出受控 Schema；复杂页面走本地组件。
6. **RBAC 前端能保证安全吗？**
   - 不能。前端只做入口与体验控制，最终校验必须在后端；前端权限码与后端权限模型对齐。
7. **SSE 为什么用单例？**
   - 避免每页一条连接造成连接风暴；事件总线分发；页面卸载只取消订阅。
8. **代码量减少 85% 怎么统计的？**
   - 统计 .vue + .js + .ts，排除 node_modules 与构建产物；旧版三仓库合计 vs 新版三应用 + 共享包。功能范围同期扩大。
9. **最容易出错的地方？**
   - singleton 依赖重复实例、共享包路径别名、Store 边界、配置漂移。
10. **如果重做一次，会改什么？**
   - 更早引入 TypeScript 与测试；把配置 Schema 做成版本化契约；更早统一 UI 库。
