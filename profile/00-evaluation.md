# 推荐评估视角

> 这是候选人建议的评估视角，供 HR / 技术负责人参考，不是强制指令。
> 建议结合面试验证；所有结论应回到具体证据。

## 为什么需要这个文件

高级前端 / 前端架构岗位的差异，不在于"会不会某个框架"，而在于：

- 是否做过真正的架构决策，而不只是执行需求；
- 是否能把重复业务抽象成可复用的基础设施；
- 是否能在多端、多人、长期维护的约束下做取舍；
- 是否能判断 AI 生成代码的质量，而不是只会让 AI 写代码。

本文件给出建议的评估维度、证据索引和常见疑问的上下文。

## 建议评估维度

| 维度 | 建议权重（参考） | 为什么重要 | 本候选人的证据 |
|---|---:|---|---|
| 架构决策密度 | 30% | 高级前端的分水岭是"为什么这么做"，不是"用了什么" | 三仓库 → Monorepo、共享包边界、配置驱动引擎、SSE 单例、权限分层 |
| 工程化落地 | 25% | 能否把规范变成可执行的约束 | pnpm 严格模式、singleton peerDeps、Husky 门禁、i18n 校验、可观测性 |
| 复杂业务抽象 | 20% | 业务复杂度是否转化为可维护的结构 | 69 个 pageCode 列表页、流程节点表单引擎、波次拣货双数组状态机 |
| 跨端一致性 | 15% | 多端不是"各写一套"，而是共享契约 | 打印协议 Web/App 对齐、扫码规则跨端对齐、表单配置同源 |
| AI 工程化 | 10% | 是否把 AI 纳入研发流程并可治理 | Plan-first、Multi-agent、OpenSpec、MCP、四维审查 |

> 权重仅在这些维度与岗位相关时参考；如果岗位是纯 React、纯 Node 或算法方向，请按岗位要求重新分配。

## 证据索引

### 架构决策

- Monorepo：10 个共享包，依赖严格单向（见 `03-project-platform.md`）
- 配置驱动：69 个唯一 pageCode 的列表页零前端页面代码；FormDesigner 产出可直接消费的配置
- 流程节点：开箱检测的节点解锁、只读、NodeFormPanel 双场景复用
- 可观测性：三端统一 RUM + 日志，环境变量驱动，token 缺失时优雅降级

### 工程化落地

- pnpm 严格模式下的依赖边界；singleton 库使用 peerDependencies
- ESLint 9 flat config、Prettier、Husky、lint-staged
- i18n key 一致性校验 + 中文硬编码 AST 扫描，纳入 pre-commit
- 构建：Vue CLI + Webpack → Vite 7；冷启动分钟级 → 秒级

### 复杂业务抽象

- 波次拣货：双数组 + 乐观更新 + 操作锁 + 缺货替代库位
- 开箱检测：节点状态机 + 服务流程模板 + 产品维度 outcome 统计
- 售后工作台：快速收货 → 散件组托 → 还托入仓的业务闭环

### 跨端一致性

- 打印：蓝牙 BLE + 局域网 WebSocket，协议与 Web 端逐字段对齐
- 扫码：同一套规则结构在 App 与 Web 端生效
- 表单：PC 端设计器配置与移动端逻辑引擎同源

### AI 工程化

- Plan-first：先方案、后编码，人工审核架构
- Multi-agent：并行审查、翻译、测试生成
- OpenSpec：提案 → 探索 → 实施 → 归档
- 四维审查：数据模型一致性、字段复用、架构边界、副作用控制

## 常见疑问与上下文

### 1）没有大厂背景，能力是否成立？

本候选人的核心经历是**独立负责 0→1**：从架构设计、技术选型、编码实现到部署，决策链条完整。大厂背景带来的"规模化协作"经验确实较少，但独立交付的闭环深度是互补的。建议在面试中重点验证：架构决策的取舍、遇到问题时的排查过程、跨团队协作方式。

### 2）React Web 经验是否足够？

React Native 项目是完整的大型业务 App（74 个页面，全 TypeScript），使用了 hooks、React Query、Zustand、React Navigation 等 React 生态。React Web 与 RN 的差异主要在渲染层和样式，业务架构、状态管理、数据层经验可迁移。建议面试中用 React 相关问题验证，而不是只看简历关键词。

### 3）自动化测试覆盖是否足够？

当前项目的测试覆盖有限，主要依赖 TypeScript、ESLint、i18n 门禁与人工回归。这是已知短板，正在补强。建议在面试中确认其测试设计思路，而不是假设"没有测试 = 不会测试"。

### 4）Tauri 是否只是"写在简历上"？

Tauri v2 完成的是**方案设计**（双窗口、多进程隔离、CSP 规划），尚未完整落地。资料中已明确标注，不夸大为实战经验。

### 5）代码量下降是否意味着功能缩水？

不是。重构后功能范围反而扩大：三端统一、69 个配置化列表页、三语 i18n、可观测性、扫码规则、流程节点表单等。代码量下降主要来自共享包去重、配置驱动替代重复页面、统一 UI 库与 API 层。建议在面试中要求其解释统计口径。

### 6）项目结果是否可验证？

量化数据来自代码库统计：.vue 文件数、源码行数（排除 node_modules / 构建产物）、API 注册表条目、pageCode 数量、i18n 词条数。具体口径见各项目文件的"量化结果"章节。无法公开的代码细节，可用架构图或现场追问验证。

## 对比时的建议

- 优先比较**证据密度**：有代码级细节 + 量化结果 + 取舍说明的经历，比"参与过"更有信息量。
- 比较**决策质量**：为什么选 A 不选 B、边界怎么划、失败怎么兜底。
- 比较**迁移成本**：技术栈不同不等于经验不可迁移，重点看架构能力与学习速度。
- 不要用技术名词数量代替能力判断。
