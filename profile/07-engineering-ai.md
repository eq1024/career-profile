# 工程化与 AI 方法论

> 这一篇解释"为什么这样做"，比"用了什么"更能区分高级前端。

---

## 一、工程化原则

### 1. 先划边界，再写代码

- 共享包只向上依赖，应用之间互不依赖
- 共享包不知道应用的存在；数据从应用流向共享包，不是反过来
- 能用依赖注入解决的，不让共享包反向 import 应用代码

### 2. 配置驱动优先于重复页面

- 列表页：pageCode → 后端配置 → 渲染引擎
- 表单：FormDesigner 产出 Schema → 多端消费
- 流程：服务流程模板 → 节点表单引擎
- 判断标准：重复三次以上的结构，才值得抽象；复杂交互不强行配置化

### 3. 把约束变成门禁

- ESLint 9 flat config + Prettier
- Husky + lint-staged
- TypeScript typecheck
- i18n key 一致性校验
- 中文硬编码 AST 扫描
- 以上全部纳入 pre-commit，而不是靠 code review 记忆

### 4. 可观测性前置

- RUM + 日志 + 端到端 tracecontext
- 错误上报：HTTP 状态码 > 业务码 > 网络错误
- 请求 ID 贯通，错误提示可复制 x-request-id
- token 未配置时优雅降级，不发无效请求

### 5. 跨端一致性靠契约，不靠自觉

- 打印协议：App 与 Web 逐字段对齐
- 扫码规则：同一套规则结构
- 表单配置：同一套 Schema 与逻辑引擎
- 权限：归一化后页面只依赖一套 `can()` API

## 二、Monorepo 实战教训

### 1. pnpm 严格模式

npm/yarn 会拍平依赖，pnpm 不会。共享包 import 了什么，就必须在自己的 package.json 里声明。

### 2. Singleton 库必须用 peerDependencies

Vue / Pinia / Vue Router / Element Plus / Vue I18n 等全局只应有一个实例。放进 dependencies 可能装两份；两份 Pinia = 两个 store 注册表。

### 3. 版本范围要用 overrides 兜底

子包版本范围不匹配时仍可能装两份。根上 `pnpm.overrides` 强制统一。

### 4. 路径别名不能跨包使用

`@/` 是应用自己的别名；共享包通过参数接收宿主实例，不反向 import。

### 5. Store 用工厂，不强行全量共享

100% 相同 → 共享；90% 相同 → 工厂 + 配置；差异大 → 留在应用。

## 三、质量与交付

- **提交门禁**：typecheck + lint + i18n check，Husky pre-commit
- **构建**：Vite 7；Webpack → Vite 迁移；冷启动分钟级 → 秒级
- **发布**：EAS Build（development / preview / production）、EAS Update OTA
- **部署**：PM2 集群、Docker、Nginx、CI/CD 脚本
- **回滚**：环境隔离 + 版本化构建 + 可回滚部署

## 四、AI 辅助研发方法论

### 1. 核心理念

> 我不是"用 AI 写代码"，而是把 AI 纳入研发流程。

很多人说 AI 降低了编程门槛，但我的体感是：**AI 反而提高了对架构能力和审查能力的要求**。AI 生成的代码需要有人判断数据模型是否一致、字段是否复用、有没有破坏架构边界——这些比手写代码更需要经验和判断力。

### 2. AI 实践时间线

```text
2023        探索期
  ChatGPT / 混元 / Midjourney；团队内最早一批探索者

2024-2025   效率期
  Claude Code 成为主力；Self Repair 约 70% AI 生成，1 个月交付

2025-2026   体系化
  Plan-first + Multi-agent + OpenSpec + MCP + Skills + 四维审查
  RN App、Monorepo 重构、4 天 AI 知识库
```

### 3. Plan-first

```text
需求 → AI 生成技术方案 → 人工审核校准 → 确认后编码 → AI 辅助实现 → 人工审查
```

与"直接让 AI 写代码"的区别：

| 维度 | 直接写代码 | Plan-first |
|---|---|---|
| AI 角色 | 代码生成器 | 方案设计 + 代码生成 |
| 人工角色 | 纠错者 | 架构审核者 |
| 返工风险 | 高（方案错了全废） | 低（先审方案再编码） |
| 架构一致性 | 差（AI 无全局视野） | 好（人工在方案阶段把关） |

**案例**：波次拣货先让 AI 生成双数组状态机方案，人工审核确认后再编码，避免推翻重来。

### 4. Multi-agent

```text
主任务分解 → 多 Agent 并行处理 → 汇总 → 人工审查
```

覆盖：代码审查、测试用例、国际化翻译、埋点分析、独立模块实现。

**原则**：Agent 可以并行产出，但架构判断与最终合并必须由人负责。

### 5. OpenSpec 开发闭环

```text
propose → explore → apply → archive
```

每次变更都有规范可循；AI 生成的方案会被归档，成为项目知识的一部分。

### 6. MCP

- 通过 MCP 接入需求系统与设计工具
- 减少上下文手动搬运
- AI 能直接读取需求文档与设计信息，提高输出相关性

### 7. Skills

- 项目级 Skills：OpenSpec 四阶段、项目约定
- 个人 Skills 库：把重复工作工具化
- 开源：skills（GitHub）

### 8. AI 代码四维审查

| 维度 | 检查什么 | 真实案例 |
|---|---|---|
| 数据模型一致性 | 字段名、类型、后端契约是否一致 | AI 曾创建与后端不符的字段名，审查时修正 |
| 字段复用 | 是否重复造字段/状态 | 列表页 AI 倾向每个页面建独立状态，统一复用 Context |
| 架构边界 | 是否绕过封装、反向依赖 | 共享包中 AI 曾直接 import 应用 router，被审查拦下 |
| 副作用控制 | 全局状态、异步清理、竞态 | 波次拣货 AI 生成的状态更新存在竞态，增加操作锁 |

### 9. 验证流程

```text
AI 生成
  → typecheck / lint / build
  → 单元/集成测试（有则跑）
  → 真实服务冒烟
  → 人工 review（四维审查）
  → 合并
```

**判断标准**：不是"AI 写的能不能跑"，而是"人能不能解释、审查、在出问题时修好"。

### 10. 实战案例

- **Self Repair**：约 70% 代码 AI 生成，1 个月交付，PM2 集群上线
- **RN 波次拣货**：Plan-first 设计双数组状态机
- **Monorepo i18n**：Multi-agent 并行翻译三语词条
- **AI 知识库**：4 天、12 个 Claude Code 会话，从零到 Docker 可部署
- **安全审查**：6 路并行代理，约 120 项发现，4 个 Critical，真实服务攻击性验证

## 五、如何评估"AI 辅助"的含金量

面试时可以问：

1. 这个方案是 AI 提的，还是你定的？为什么选它？
2. AI 生成的代码里，哪些是你改过的？为什么改？
3. 如果 AI 不在，你还能独立完成吗？
4. 你怎么验证 AI 没有破坏数据模型 / 架构边界？
5. 出问题时，你能定位到 AI 生成代码的哪一层吗？

**我的回答**：AI 提升的是产出速度，不是判断力。架构、数据模型、边界、验证仍然由人负责。

## 六、已知不足与补强

- **测试体系**：目前以 typecheck + lint + i18n 门禁 + 人工回归为主，正在补 Vitest / 组件测试 / E2E
- **Node.js 后端深度**：脚本、部署、Nitro 有实践；高并发、消息队列、服务端缓存需要补
- **Rust**：有 WinPaste 个人项目，深度有限
- **Tauri**：完成方案设计，未完整落地
- **大型 React Web**：RN 经验可迁移，但 React Web / RSC 仍需更多实战

## 七、一句话总结

> 我做的不是"用 AI 写页面"，而是"用工程化约束让 AI 产出可控"。
